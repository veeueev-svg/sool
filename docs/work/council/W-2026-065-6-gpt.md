## عيب جديد: قيمة `from` المتعارضة تضيع قبل المقارنة

معيار القبول نفسه يوجب أن يسجل `rate_amended` القيمتين، القديمة والجديدة. لكن `collect` في `rehydrate_fiscal.ts` يبني شاهد الاستعادة من:

```text
base = detail.base
ratePerMille = detail.to
declaredAt = detail.effectiveFrom
commandId = detail.commandId
```

ولا ينقل `detail.from`. كما أن `RateAmendmentRecovery` و`restored` لا يحملانها. لذلك يمر زوج الشاهدين التاليين بلا خطأ:

```text
{ base: 'compute_usage', from: 25,  to: 80, effectiveFrom: at, commandId: 'cmd:x' }
{ base: 'compute_usage', from: 999, to: 80, effectiveFrom: at, commandId: 'cmd:x' }
```

التنفيذ الفعلي أعاد `1`، طبّق الأول، ثم تخطى الثاني؛ فلا يصدر `RECOVERY_RATE_COMMAND_CONFLICT`. هذا تعارض في قيمة تاريخية واجبة الحفظ، لا إعادة شاهد أمينة. والاختبار الحالي لا يمكنه كشفه لأنه يسقط `from` قبل طبقة المقارنة.

ينبغي أن تحمل حمولة الاستعادة القيمتين، وأن يقارن التكرار جميع حقول شاهد `rate_amended` ذات المعنى (وأن يتحقق، حيث يلزم، من أن `from` يوافق الإعلان السابق). لا يكفي أن يطابقا الوجهة النهائية نفسها كي يسكت اختلاف الإثبات التاريخي.
