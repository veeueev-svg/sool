## 2) مراجعة شفرة العلاجين والتوسيع المعلن

راجعتُ الشفرة في شجرة التجميد لموضعي العلاج وتوسيع النطاق المعلن في الجلسة 148:

### 1. علاج عيب `TAX_LEVY_SINK_NULL_DECLINE_SWALLOWED`
- **الموطن:** `src/economy/tax.ts` الدالة `commit()`.
- **التحليل:**
  كانت الشفرة في الجولة 50 تتجاهل قيمة الإرجاع لدالة `sink.record()` مكتفية بـ `try/catch`، مما جعل الرفض التعاقدي (ردّ `null` من الوسيط بمعنى "لم يُدوَّن") يمرّ كأنه نجاح دائم بلا رمي ولا إقفال.
  العلاج المطبّق:
  ```typescript
  const recorded = this.sink?.record('tax_levy', { levy: { ...levy }, sequence: this.sequence });
  if (recorded === null) throw new Error('TAX_LEVY_SINK_NULL_DECLINE');
  ```
  عندما يردّ الوسيط `null`:
  - يُرمى الخطأ `TAX_LEVY_SINK_NULL_DECLINE`.
  - تلتقطه كتلة `catch(err)` فترمي `TAX_LEVY_SINK_OUTCOME_UNKNOWN` بعلّته المسمّاة (`cause: err`).
  - يُضبط المتغيّر الداخلي `this.sinkOutcomeUnknown = true`.
  - تفحص الدالة `assertOpen()` هذا المتغيّر في مطلع كل من `assess` و`collect` و`waive`، فترمي `REVENUE_SINK_OUTCOME_UNRESOLVED` حتى يُعاد الإقلاع.
  - عند إعادة الإقلاع (`restore`)، يُعاد ضبط `sinkOutcomeUnknown = false` وتُبنى الحالة الحقيقية من اليومية.
  - إذا كان `this.sink` غير مربوط أصلاً (`null`)، فإن `this.sink?.record(...)` يعيد `undefined` (وليس `null`) فلا يُرمى استثناء، وهو السلوك المتوافق مع التهيئة قبل ربط اليومية.

### 2. علاج عيب `COLLECT_TREASURY_RECEIPT_TAX_LEVY_SPLIT_DOUBLE_RECEIPT`
- **الموطن:** `src/economy/treasury.ts` الدالة `receive()`، واستدعاؤها في `src/economy/tax.ts` الدالة `collect()`.
- **التحليل:**
  كان التحصيل في الجولة 50 يُنشئ إيصالاً دائمًا في الخزانة (`treasury.receive` يدوّن قيدًا في الدفتر ويُلحق شاهد `revenue_received` في سجل التدقيق) قبل محاولة قيد `tax_levy` في اليومية. فإذا فشل قيد اليومية، بقي الإيصال المالي مسجلاً في الخزانة برصيده المالي، بينما بقي الرسم في اليومية بحال `assessed`، فإذا أعيد التحصيل بعد الإقلاع أُنشئ إيصال ثانٍ وتضاعف الرصيد (من 75,000 إلى 150,000).
  العلاج المطبّق:
  - أصبحت الدالة `treasury.receive` تقبل معاملاً اختياريًا `idempotencyKey?: string`.
  - يمرر `RevenueService.collect` معرّف الرسم `levy.levyId` كمفتاح حتمي: `receiptId = idempotencyKey === undefined ? rcpt:${this.sequence + 1} : rcpt:lk:${idempotencyKey}`.
  - قبل قيد أي عملية جديدة في الدفتر، تستعلم الخزانة عن وجود قيد سابق بالمعرّف الحتمي:
    ```typescript
    if (idempotencyKey !== undefined) {
      const prior = this.deps.ledger.entry(receiptId);
      if (prior !== null && prior.total === amount
        && !this.deps.ledger.journal().some((e) => e.reverses === receiptId)) {
        return {
          ok: true, auditId: prior.auditId,
          disbursement: { disbursementId: receiptId, line: 'revenue', amount: prior.total, to: this.deps.account,
            purpose: prior.memo, by: prior.by, at: prior.at, royalCommandId: null, entryId: prior.entryId },
        };
      }
    }
    ```
  - إذا وجد القيد القائم وكان المبلغ مطابقًا وغير معكوس: يُعاد الإيصال القائم دون إنشاء قيد دفتر جديد، ودون إضافة شاهد تدقيق جديد، ودون زيادة عدّاد التسلسل `this.sequence`، ودون مضاعفة رصيد الخزانة.
  - إذا كان القيد معكوسًا (`reverses === receiptId`)، فإن الشرط يتجاوز استئناف الإيصال ويحاول القيد مجددًا، فيرفضه الدفتر لكون المعرّف مكررًا (`معرّف قيد مكرَّر — لا إثبات مرتين`)، وهو الحد المعلن في الملحق.
  - إذا لم يُمرر مفتاح (الاستدعاء العام للخزانة)، يستمر سلوك التسلسل الحسابي `rcpt:${this.sequence + 1}` بلا أي تأثير جانبي، مع تمايز بادئة المعرّف (`rcpt:lk:` مقابل `rcpt:`).

  - رُمي استثناء `TAX_LEVY_SINK_OUTCOME_UNKNOWN` بعلّة الأصل `TAX_LEVY_SINK_NULL_DECLINE`.
  - أُقفلت الخدمة فورًا: محاولة `assess` أو `collect` بعدها رُميت برمز `REVENUE_SINK_OUTCOME_UNRESOLVED`.

### المسبار 2: الرفض التعاقدي (ردّ null) في مسار التحصيل (`collect`)
- **الإجراء:** تقدير رسم (مبلغه 75,000)، ربط وسيط يردّ `null` عند قيد `tax_levy`، استدعاء `collect`.
- **النتيجة المقيسة:**
  - رُمي استثناء `TAX_LEVY_SINK_OUTCOME_UNKNOWN` بعلّة `TAX_LEVY_SINK_NULL_DECLINE`.
  - وُجد إيصال الخزانة الدائم بحصيلة 75,000 وشاهد `revenue_received` واحد.
  - عند إعادة الإقلاع من اليومية الحقيقية: استُعيد الرسم بحال `assessed`، وبقي رصيد الخزانة 75,000 مع إيصال واحد.
  - عند إعادة استدعاء `collect` بعد الإقلاع: نجحت العملية (`ok: true`)، واستؤنفت بالإيصال نفسه (`receiptEntryId: rcpt:lk:levy:1`)، وظل رصيد الخزانة 75,000 (لم يتضاعف إلى 150,000)، ولم يُضف شاهد ثانٍ في التدقيق (بقي شاهد `revenue_received` واحد فقط)، وأصبحت حالة الرسم `collected`.

### المسبار 3: رمي الوسيط استثناءً في مسار التحصيل مع إقلاع متكرر ثلاثي
- **الإجراء:** محاكاة انفجار وسيط اليومية برمي استثناء أثناء التحصيل، ثم تنفيذ دورتي إقلاع متتاليتين من القرص.
- **النتيجة المقيسة:**
  - رُمي `TAX_LEVY_SINK_OUTCOME_UNKNOWN`، وسُجّل الإيصال المالي الأول برصيد 75,000.
  - بعد الإقلاع الأول: نجحت إعادة التحصيل بالإيصال القائم واستقر الرصيد عند 75,000.
  - بعد الإقلاع الثاني: ظلت حالة الرسم `collected`، وظل الرصيد 75,000، وبقي شاهد الإيراد واحدًا وسلسلة التدقيق سليمة تمامًا.

### المسبار 4: الرفض التعاقدي في مسار التقدير (`assess`)
- **الإجراء:** ربط وسيط يردّ `null` عند قيد `tax_levy` واستدعاء `assess`.
- **النتيجة المقيسة:**
  - رُمي `TAX_LEVY_SINK_OUTCOME_UNKNOWN` وأُقفلت الخدمة.
  - بعد إعادة الإقلاع: لم يُسجّل أي رسم غير مكتمل في اليومية (`outstanding().length === 0`)، ولم تتأثر سلامة التدقيق.

### المسبار 6: استقلالية عدّاد التسلسل `rcpt:N` عن مفاتيح الحتمية `rcpt:lk:...`
